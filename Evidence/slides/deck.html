A4 · Refund money flow

What one refund writes, and how settlement sees it

Ledger group per successful refund (balanced, one entry_group_id)

AccountSideAmount
merchant_payabledebitrefund gross
card_scheme_clearingcreditrefund gross
platform_fee_revenuedebitfee reversed
merchant_payablecreditfee reversed
  • Refundable = captured − refunded − pending reservations, checked under the same row lock as capture and void.
  • Each partial refund reverses its share of the fee; the last one reverses whatever is left, so reversals add up to the fee charged.
  • POST /v1/refunds needs owner or finance role and an Idempotency-Key; omitted amount = everything still refundable.
  • One refund.succeeded outbox event per success; timeline records refund_partial or refunded.

Settlement and reporting

  • CloseBatch subtracts succeeded, unbatched refunds from the same Bahrain business day: gross loses amount_fils, fee loses fee_reversed_fils. Refunds are stamped with the batch ID, so a second close does not count them again.
  • Reconciliation counts an unbatched refund in pending net (amount_fils − fee_reversed_fils), so ledger, closed batches and pending still meet.
  • Reporting adds refund_count and refund_gross_fils to merchant_daily_volume for the Bahrain date.
  • Shipped behind FEATURE_REFUNDS (code default off; set in dev compose). Production reads it from the server env file: [NEEDED: confirm it is on]

Capacity errors: 0 at every level. No HTTP 500s, no client timeouts.

Method

  • Node.js 22 fetch closed-loop runner (k6 not installed); about 8 s per level.
  • Fixed scenario: GET /v1/payment-links/:token → POST …/pay, 1,000 fils (1.000 BD), Idempotency-Key, one fresh link per iteration.
  • Bar: end-to-end p95 ≤ 1,500 ms and ≤ 1% unexpected failures (simulator’s default 2% decline/error counted separately).
  • Caps for the run: API 0.50 CPU / 512 MiB · Postgres 0.30 / 768 MiB · settlement 0.10 / 256 MiB · reporting 0.10 / 256 MiB.

Bottleneck

API Postgres pool of 5 connections held across two acquirer-simulator sleeps (100–400 ms each) in the measured image. 5 slots × ~0.5 s ≈ 10 checkouts/s; measured plateau 9/s. API CPU peaked ~11% of a 50% quota; RSS ~165–170 of 512 MiB; five sessions “idle in transaction” waiting on the app.

Overload and recovery

No rate limit or 503 shedder on the public pay route; excess requests queue for a pool slot (5 s connection timeout). After the 36-user wave, 4 users: 53/53 paid, p95 686 ms, same process. Dev compose restart policy is no; production compose uses unless-stopped.

Money check (run capload-1793375189959, 420 links)

399 paid · 399 transactions captured at 1,000 fils = 399,000 fils (399.000 BD) · 0 duplicate transaction IDs · 21 links back to active (simulator declines/errors). 9 failures left an authorized transaction with an active 1,000-fil hold while the link returned to active (9.000 BD reserved). This was a finding in the measured image’s pay.ts.

Caveat

The measured image was not the working-tree code: working-tree authorize.ts/capture.ts release the connection before the acquirer call, and its pay.ts voids a definitive decline. [NEEDED: re-run on the final deployed build]
