## Root cause and architecture

Production had zero merchant and merchant-user records. The existing public signup inserts a merchant with default active/live mode, then a profile and owner in one transaction. Settlement RunDailyBatch selects all active merchants with test_mode=false, and CloseBatch may create an empty settlement batch. Signup cannot safely provision a test merchant while the live daemon runs. No administrative test-mode creation/change operation was found; destructive seed fixtures are not a production provisioning path.

Inspected context/README.md, AUTH_AND_SECURITY, DATABASE, DEPENDENCY_MAP, DECISIONS and settlement context; docs/ARCHITECTURE.md and ADR 0001; merchant/user migrations, seed helpers, signup, transaction helper, public route, auth handlers, settlement selection and close, existing TS/Go tests. Current source wins over stale docs: architecture still says password plus email OTP; f4b5a1a accepts password-only for unenrolled accounts. DATABASE context also has stale merchant status/name descriptions. ADRs 0003/0004/0006 and HANDOVER have outstanding financial-policy conflicts; this change does not decide them. No schema change, protected money change, settlement code change or partner API change was made.

Merchant insert includes test_mode before profile and owner are written, all inside the existing transaction. Failure rolls back; no update-after-creation or committed live-mode intermediate state is used.
- `apps/api/src/onboarding/provisionTestMerchant.ts`: separate operator command, no network route, with explicit `--confirm-test-merchant`; accepts a bounded JSON signup document and a password of 20–128 characters on stdin, emits only merchant and owner IDs and reports generic errors. OS/operator access to the executable and database credentials is the authorization boundary; the flag is explicit intent, not authentication. In production use, restrict access to both credentials and command execution and supply stdin privately without shell history, process arguments, files or logs. Account/profile details and temporary password must be chosen via an authorized secure channel. The command has not been deployed or used.
- Public HTTP request bodies cannot control the boolean: public signup continues to call the live-only function. Settlement eligibility logic is unchanged.
