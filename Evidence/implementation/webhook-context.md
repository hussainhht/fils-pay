# Webhook architecture context dossier

Date: 2026-10-30. Baseline HEAD: `13d8161`. Scope: read-only source inspection of outbound webhooks, inbound acquirer callbacks, and immediate producers. No vulnerability verdicts or implementation changes. No runtime/test execution in this workstream. Initial `git status --short` was clean.

## Reachability and ownership

- FilsPay supports both directions. `apps/api/src/app.ts:68` registers merchant endpoint management at `/v1/merchants/:merchantId/webhook-endpoints`; `app.ts:73` registers inbound `/v1/acquirer/callbacks`. The latter is informational fraud review, not payment confirmation (`acquirer/callbacks.ts:27`).
- Merchant routes authenticate, restrict roles, and compare path merchant ID with authenticated tenant (`routes/webhooks.ts`, `assertOwnMerchant`). Owner/finance can manage endpoints, test-send and replay; support additionally reads delivery history. Creation explicitly calls `requireMerchantWriterActor`; delete, patch, test-send and replay do not call that helper in their handlers. Whether the common authentication/role hook supplies equivalent actor restrictions remains an open question for subsequent assessment.
- Financial producers -> `outbox_events` -> dispatcher -> `webhook_deliveries` -> injected HTTP transport. Reporting independently consumes outbox rows; dispatcher explicitly ignores `processed_at` (`webhooks/dispatcher.ts:13`). `index.ts:31` starts the worker after listen; `buildApp` never starts it.

## Contracts and durability

- Actual event set: `transaction.captured`, `transaction.voided`, `refund.succeeded`, `settlement.paid` (`dispatcher.ts:28`, `envelope.ts:9`). No current outgoing authorized/failed/expired contract was found in inspected event definitions. `settlement.batch_closed` exists internally but is not delivered.
- Envelope `{id,type,createdAt,data}`; HMAC header `Webhook-Signature: t=<seconds>,v1=<sha256hex>` signs `${timestamp}.${canonicalJson(envelope)}`. `Webhook-Delivery-Id` matches envelope ID; retries and replay retain identity while signing with current time (`sign.ts`, `headers.ts`, `replay.ts:41`). Receiver must verify freshness and deduplicate ID. The signature itself does not stop repeated processing within the freshness window.
- Capture emits atomically with ledger/status and completed idempotency key (`payments/capture.ts:227,335`). Void emits inside `withTransaction` (`payments/void.ts:42,96`). Refund emits `refund.succeeded` alongside successful full/partial refund accounting (`payments/processRefund.ts:504`), carrying refund ID and cumulative totals. Settlement notification scans already-paid batches and inserts once via migration 0078 uniqueness (`settlement/internal/settlement/payout_notify.go:88`); this is recovery scanning rather than insertion in the payout transaction itself.
- `0021_webhook_endpoints.sql` stores merchant URL, encrypted secret, display prefix, status and creator. Trigger publishes `outbox_events_channel`; PostgreSQL delivers notifications after commit. `0022_webhook_deliveries.sql` persists envelope, identity, attempt count, last HTTP status/body excerpt, schedule, replay ancestry. Retries update that row, not a separate per-attempt history table. Archive history exists in migration 0068.
- Backoff base 30 seconds, cap six hours, +/-10% jitter; default eight attempts, ten-second HTTP timeout, five-second poll (`config.ts:296`). Worker polls independently of notification and reconnects listener (`dispatcher.ts:296`). Restart recovery relies on durable pending rows becoming due after their lease.
- Secrets use random 24-byte tokens and AES-256-GCM (12-byte random IV, 16-byte tag, 32-byte configured key). Creation intentionally returns plaintext once to the authorized merchant; list/detail use prefix only. `cancel.ts:18` disables an endpoint with delivery/archive history and hard-deletes only history-free endpoints; its old hard-delete docblock is stale.

## Context discrepancies and open questions

- `context/modules/packages-events.md` documents an obsolete helper signature and `transaction.authorized`/`refund.created`; actual definitions differ. `context/DEPENDENCY_MAP.md` and `context/ARCHITECTURE.md` name the wrong notification channel and imply authorized delivery. `context/modules/apps-api.md` still lists replay identity as unresolved despite current identity-preserving code.
- Required failed-payment / expired-link notifications need product/spec confirmation: current event contract omits them, and inspected `paymentLinks/pay.ts:65` treats expiry as derived from timestamp without a new outbox event. Merely adding dispatcher types would not establish a producer or public payload contract.
- Delivery exceptions before a normal transport result do not consume bounded attempts; malformed internal payload handling and worker lease/outcome races require subsequent focused inspection, not conclusions in this dossier.
